# Backend fix needed: variant `attributes[].key` still rejects Arabic

## Summary

The dashboard now lets sellers name a custom variant option (e.g. "weight" / "الوزن") in
Arabic or English. Saving a variant with an Arabic option name fails with a 422 from the API:

```json
{
    "detail": [
        {
            "type": "string_pattern_mismatch",
            "loc": ["body", "payload", "attributes", 2, "key"],
            "msg": "String should match pattern '^[a-z][a-z0-9_]*$'",
            "ctx": { "pattern": "^[a-z][a-z0-9_]*$" }
        }
    ]
}
```

This is a **Pydantic schema validation error**, thrown before any endpoint/business logic
runs. The dashboard is sending the request correctly (verified: nothing on the frontend
rewrites or strips the key) — the schema field itself still enforces the old ASCII-only
pattern.

## Why this wasn't caught by the earlier "dynamic attributes" fix

The earlier work (documented in `.docs/VARIANT_ATTRIBUTES.md` / `CHANGELOG_DYNAMIC_ATTRS.md`)
updated the **read/filter path** — `_parse_attr()` and the dynamic filtering in
`products/api.py` that lets `GET .../public?attr=weight:1kg` accept arbitrary keys when
*querying* variants.

That is a different code path from the **write path** — the schema that validates a
variant's `attributes[].key` when a seller *creates or updates* a variant. That schema
still has the original constraint.

## Where to look

- `products/schemas.py` — `VariantCreateSchema` / `VariantUpdateSchema` (or wherever the
  attribute item schema is defined, e.g. `VariantAttributeInSchema`), field `key`.
- `mall/schemas.py` — the equivalent schema for `MollProductVariant` / `MollVariantAttribute`
  (per `d.md`, there are two independent variant systems — products/ and mall/ — both need
  the same fix).
- Wherever `attribute_key`'s `UNIQUE(variant_id, attribute_key)` / DB column length is
  defined — confirm the column can store UTF-8 (Arabic) text, not just ASCII.

## What needs to change

The field currently looks something like:

```python
key: str = Field(pattern=r"^[a-z][a-z0-9_]*$")
```

**Python's built-in `re` module (which Pydantic uses for `pattern=`) does not support
Unicode category classes like `\p{L}`.** So this can't just be a regex string swap the way
the query-param parser might have been fixed. Options, roughly in order of preference:

**Option A — custom validator (recommended):**

```python
import re
import unicodedata
from pydantic import field_validator

_ALLOWED_KEY_RE = re.compile(r"^[^\W\d_](?:[\w]*)$", re.UNICODE)
# ^^ \w with re.UNICODE matches Unicode letters/digits/underscore; [^\W\d_] excludes
# digits/underscore for the first character while still allowing Unicode letters
# (Arabic, English, etc.) — adjust to match the exact bytes you want to allow/exclude
# (no spaces, colons, or commas, since those delimit `attr=key:value,key2:value2`).

class VariantAttributeInSchema(Schema):
    key: str
    ...

    @field_validator("key")
    @classmethod
    def validate_key(cls, v: str) -> str:
        if not _ALLOWED_KEY_RE.match(v):
            raise ValueError(
                "key must start with a letter (any language) and contain only "
                "letters, numbers, and underscore — no spaces, colons, or commas"
            )
        return v
```

**Option B — use the third-party `regex` package** (supports `\p{L}`, `\p{N}` directly),
if it's already a dependency or acceptable to add:

```python
import regex
_ALLOWED_KEY_RE = regex.compile(r"^[\p{L}][\p{L}\p{N}_]*$")
```

Either way, the **allowed character set** should match what the dashboard now validates
client-side, so a name that passes on the frontend also passes on the backend:

- Must start with a letter (any language — Arabic, English, etc.)
- Followed by letters, digits, or underscore only
- No spaces, colons (`:`), or commas (`,`) anywhere — those are the delimiters in the
  `attr=key:value,key2:value2` query format, so allowing them in a key would make that
  format ambiguous to parse back.

## How to verify the fix

Reproduce with (adjust host/token/product id — this hits whichever variant endpoint the
dashboard calls: `POST /api/products/{product_id}/variants`):

```bash
curl -X POST 'https://v2.taswouk.com/api/products/<product_id>/variants' \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: application/json' \
  -d '{
    "price": 100,
    "attributes": [
      { "key": "color", "value_en": "red", "sort_order": 0 },
      { "key": "الوزن", "value_en": "1kg", "sort_order": 1 }
    ]
  }'
```

(`"الوزن"` is `الوزن` — "weight" in Arabic.)

Expect a `2xx` response with the variant created and `attribute_key` stored as `الوزن`
(or whatever normalization/casing you choose — the dashboard reads back whatever the API
returns, it doesn't assume lowercase).

Please apply the same fix + test to **both** `products/` and `mall/` variant endpoints,
since they're independent implementations.
